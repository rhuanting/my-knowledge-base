# 电商 Agent 写功能设计

## 核心判断

电商 Agent 的写功能不应该被设计成“模型直接操作平台”，而应该被设计成一个受控的操作编排层。

Agent 负责理解用户意图、生成方案、解释影响和组织执行流程；真正的写入必须经过业务 API、权限校验、规则校验、风险评估、用户确认、审计记录和回滚机制。

一句话总结：

> Agent 不直接拥有写权限，而是在受控业务工具之上，优先生成草稿，逐步开放低风险执行，最后才进入有限授权的自动运营。

## 为什么不能直接写

电商写操作往往会影响商家的真实经营结果，例如商品价格、优惠券、活动报名、库存、广告预算、商品上下架、用户触达等。

如果 Agent 直接写入系统，主要风险包括：

- 错误操作造成商家损失。
- 错误建议导致亏损、库存不足或履约风险。
- 越权调用平台能力。
- 批量操作放大单次错误。
- 操作结果难以追责。
- 部分操作无法完全回滚。
- 商家对 Agent 失去信任。

因此，写能力的设计重点不是“让 Agent 更自由”，而是“让 Agent 在明确边界内可靠地行动”。

## 写操作分级

应先把写操作按风险分层，而不是笼统地讨论 Agent 是否可以写。

| 等级 | 类型 | 示例 | 处理方式 |
|---|---|---|---|
| L0 | 只读查询 | 查询商品、订单、流量、活动规则 | 可直接执行 |
| L1 | 生成草稿 | 商品标题草稿、优惠券方案、活动报名材料 | 只保存草稿，不生效 |
| L2 | 低风险写入 | 创建未发布优惠券、保存配置草稿、添加内部备注 | 用户确认后执行 |
| L3 | 中风险写入 | 发布优惠券、修改商品信息、报名活动、批量修改少量商品 | 变更摘要 + 二次确认 |
| L4 | 高风险写入 | 批量改价、自动投放预算、自动下架商品、发放大额券 | 审批、限额、白名单、灰度 |
| L5 | 禁止执行 | 绕过平台规则、修改结算、删除关键经营数据 | Agent 只能解释，不能执行 |

这个分级应沉淀到工具和权限系统中，而不是只写在 prompt 里。

## 草稿优先

电商 Agent 写能力最适合采用“草稿优先”的默认模式。

标准流程：

```text
用户提出目标
  ↓
Agent 理解意图
  ↓
Agent 查询数据和规则
  ↓
生成操作方案
  ↓
生成草稿
  ↓
展示影响范围和风险
  ↓
用户确认
  ↓
系统执行
  ↓
记录审计
  ↓
追踪效果
```

例如用户说：“帮我给这个商品做一个老客召回券。”

Agent 不应直接发布优惠券，而应生成类似方案：

- 人群：近 90 天购买过但近 30 天未复购用户。
- 券类型：满 99 减 10。
- 有效期：3 天。
- 发放上限：500 张。
- 最大成本：5000 元。
- 风险：如果商品毛利率低于 12%，可能压缩利润。

对应动作可以是：

- 生成草稿。
- 修改方案。
- 确认发布。
- 取消。

早期产品尤其应该多做“草稿”和“辅助填写”，少做“自动生效”。

## 工具层设计

Agent 不应直接连接数据库，也不应通过自由 SQL 修改业务数据。它只能调用经过封装的业务工具。

示例工具：

```text
create_coupon_draft()
publish_coupon()
update_product_title()
submit_campaign_application()
adjust_inventory_warning_threshold()
create_operation_task()
```

每个写工具都应该具备：

- 明确的参数 schema。
- 用户身份和权限校验。
- 业务规则校验。
- 风险等级标识。
- dry-run 预演能力。
- 幂等 key。
- 变更摘要。
- 审计日志。
- 回滚或补救策略。

Agent 是调用者，不是最终裁判。最终是否允许执行，应由工具层、权限系统和风控系统共同决定。

## Dry-run 预演

所有重要写操作都应先 dry-run。

dry-run 的作用是让系统在真正写入之前回答：

- 即将影响哪些对象？
- 写入前是什么状态？
- 写入后会变成什么？
- 是否满足平台规则？
- 是否触发风险阈值？
- 最大成本或最大损失是多少？
- 哪些影响可以回滚，哪些不能回滚？

例如折扣活动预演应返回：

- 影响商品。
- 原价和活动价。
- 当前毛利率和活动后毛利率。
- 当前库存。
- 预计最大让利。
- 是否存在亏损风险。
- 是否建议继续发布。

只有 dry-run 通过，才进入确认和执行。

## 用户确认

高质量确认不应该只是让用户在聊天中回复“确认”。

确认页或确认卡片应结构化展示：

- 即将执行的操作。
- 影响对象。
- 核心参数。
- 生效时间。
- 成本上限。
- 可能风险。
- 可撤销内容。
- 不可撤销影响。
- 操作人和权限身份。

例如：

```text
即将执行：
- 创建优惠券：满 99 减 10
- 投放人群：老客未复购人群
- 发放数量：500
- 有效期：2026-05-11 至 2026-05-14
- 最大成本：5000 元
- 不可撤销影响：已领取优惠券不能强制收回
- 可撤销内容：可以停止继续发放
```

操作按钮应是明确动作：

- 确认创建草稿。
- 确认发布。
- 返回修改。
- 取消。

对于高风险操作，可以要求用户输入金额、商品数量、活动名称等关键信息，避免误触。

## 权限设计

权限判断必须在工具层完成，不能相信 Agent 自己判断。

正确链路：

```text
Agent 请求调用工具
  ↓
工具层读取当前用户身份
  ↓
权限系统校验
  ↓
业务规则校验
  ↓
风控系统校验
  ↓
允许或拒绝
```

权限建议细分到：

- 是否可以查看数据。
- 是否可以创建草稿。
- 是否可以发布。
- 是否可以批量操作。
- 是否可以修改价格。
- 是否可以操作营销预算。
- 是否可以影响多个店铺。
- 是否需要上级审批。

Agent 可以解释权限不足，但不能绕过权限。

## 风险策略

Agent 写操作前，应经过独立的风险策略引擎。

典型规则：

- 单次优惠成本不能超过阈值。
- 活动后毛利率不能低于阈值。
- 批量修改商品数不能超过阈值。
- 自动发券人数不能超过阈值。
- 投放预算不能超过日预算。
- 库存不足时不能报名特定活动。
- 新商家不能使用高风险自动化。
- 处罚中店铺不能执行特定营销动作。

这些规则应由确定性的策略系统执行，而不是依赖大模型临场判断。

## 审计与追溯

所有写入必须可追溯。

审计日志至少记录：

- 谁发起的。
- 通过哪个 Agent 发起。
- 用户原始指令是什么。
- Agent 生成了什么方案。
- 调用了哪个工具。
- 传入了什么参数。
- dry-run 结果是什么。
- 用户如何确认。
- 实际写入了什么。
- 写入前后差异。
- 是否可回滚。
- 执行结果如何。

审计不仅是合规要求，也是排查纠纷、优化 Agent 和评估产品效果的基础。

## 回滚与补救

写操作应明确区分可回滚性。

可完全回滚：

- 草稿配置。
- 未发布活动。
- 未生效商品修改。

可部分回滚：

- 已发布优惠券可以停止继续发放，但已领取不可强制收回。
- 已报名活动可以撤回，但可能影响资格。
- 已修改商品信息可以恢复旧版本，但搜索权重影响不一定可恢复。

不可完全回滚：

- 已发送消息。
- 已消耗广告预算。
- 已生效价格导致的成交。

确认前必须告诉用户操作属于哪一类。

## 三种产品模式

### 1. 助手模式

Agent 只建议，不执行。

适合：

- 新人运营。
- 商家咨询。
- 平台规则解释。
- 经营诊断。

这是最安全的起步形态。

### 2. 草稿模式

Agent 可以生成配置，但不发布。

适合：

- 优惠券草稿。
- 活动报名草稿。
- 商品优化草稿。
- 营销计划草稿。
- 经营日报草稿。

这是最适合大规模推广的形态。

### 3. 托管模式

Agent 在明确授权范围内自动执行。

授权边界应包括：

- 店铺范围。
- 商品范围。
- 可执行操作。
- 成本上限。
- 有效期。
- 触发条件。
- 执行频率。
- 通知方式。

托管模式必须有清晰边界，不能做无限授权。

## 托管模式下的人机协同

托管模式适合使用 human-in-the-loop，但不适合把它做成“每一步都 ask user question”。

托管模式的核心不是频繁打断用户，而是：

> 用户提前授权边界，Agent 在边界内自动执行；一旦超出边界、风险升高、状态变化或不可逆影响出现，再触发人工确认。

也就是说，human-in-the-loop 应该从“逐次确认”升级为“边界确认 + 异常确认”。

### 适合请求用户确认的场景

托管授权前：

- 用户明确授权店铺范围、商品范围、可执行操作、成本上限、最大折扣、触发条件、执行频率和托管周期。

超出授权边界时：

- 例如用户授权单次优惠成本不超过 1000 元，但本次预计成本为 1800 元。

风险等级升级时：

- 例如原本只是创建草稿，后来需要发布。
- 例如原本只影响 5 个商品，后来影响 200 个商品。

不可逆操作前：

- 例如发送消息、消耗广告预算、发布已领取不可收回的优惠券。

业务状态发生关键变化时：

- 例如 dry-run 时库存 1000，执行时库存只剩 80。
- 例如 dry-run 时毛利率 20%，执行时毛利率变成 3%。

Agent 置信度不足或意图不清时：

- 例如用户说“力度大一点”，但没有定义预算、成本和折扣边界。

### 不适合频繁确认的场景

以下场景不应频繁打断用户：

- 每次创建草稿都确认。
- 每次读取数据都确认。
- 每次低风险、授权范围内操作都确认。
- 把用户变成 Agent 的手动确认器。

否则托管模式会退化成“更慢的后台”。

## 托管写操作的推荐模式

### 1. 授权包模式

用户不是授权某一次操作，而是授权一个可执行边界。

示例：

```text
托管目标：提升 A 商品池转化率
商品范围：商品池 X
允许操作：创建并发布优惠券
最大折扣：不超过 15%
单次最大成本：1000 元
每日最大成本：3000 元
执行频率：每天最多 1 次
持续时间：7 天
触发条件：转化率连续 2 天下滑超过 10%
通知方式：执行后通知
人工确认条件：超预算、低毛利、库存不足、影响超过 20 个商品
```

这个授权包本质上是 Agent 的行动合同。

### 2. 策略闸门模式

Agent 可以提议操作，但每个操作都必须过策略闸门。

```text
Agent 生成计划
  ↓
权限校验
  ↓
预算校验
  ↓
毛利校验
  ↓
库存校验
  ↓
风险等级校验
  ↓
授权边界校验
  ↓
允许执行 / 升级人工确认 / 拒绝
```

策略闸门必须是确定性的系统能力，不能只依赖 prompt 和模型判断。

### 3. 异常升级模式

授权范围内自动执行，异常才打断用户。

```text
正常情况：自动执行 + 通知
边界情况：暂停 + 请求确认
危险情况：拒绝执行 + 给出原因
```

这比每一步 human-in-the-loop 更适合真实运营。

### 4. 渐进托管模式

托管写操作不应一开始全量开放，可以分阶段推进：

```text
影子模式：Agent 只生成建议，不执行，观察准确率
草稿模式：Agent 自动生成草稿，用户发布
小额托管：Agent 在低预算内自动执行
扩大托管：逐步提高额度和范围
高级托管：长期策略自动运营
```

这是建立商家信任和平台风控能力的过程。

## 避免 dry-run 和 run 参数变化

写操作中最重要的工程约束之一是：dry-run 之后，实际 run 阶段不能重新传一套业务参数。

正确设计不是：

```text
dry_run(params)
run(params)
```

而应该是：

```text
prepare(params) -> immutable_execution_plan
commit(execution_plan_token)
```

也就是说，dry-run 应升级为 prepare 阶段。prepare 阶段生成不可变执行计划，commit 阶段只能提交这个计划，不能重新提交折扣、数量、商品 ID、预算等业务参数。

### 推荐流程

```text
1. prepare / dry-run
   输入用户意图和候选参数

2. 系统生成规范化执行计划
   包括最终参数、影响对象、风险结果、状态快照、版本号、有效期

3. 返回 plan_id / plan_hash / execution_token

4. 用户确认或策略自动放行

5. commit
   只传 plan_id 或 execution_token
   不允许重新传业务参数

6. 服务端校验计划未过期、状态未变化、权限仍有效、策略仍通过

7. 执行完全相同的参数
```

commit 接口只接受执行凭证，不接受业务参数。

### 执行计划应固化的内容

执行计划至少应包含：

```text
plan_id
plan_version
plan_hash
normalized_params
affected_objects
expected_state_versions
risk_level
cost_estimate
rollback_policy
authorization_scope
policy_check_result
expires_at
idempotency_key
```

其中最关键的是：

- `normalized_params`：最终要执行的参数，commit 时不可修改。
- `affected_objects`：具体影响哪些商品、优惠券、人群或活动。
- `expected_state_versions`：prepare 时相关对象的版本号。
- `plan_hash`：防止计划参数被篡改。
- `expires_at`：防止很久以前的计划被执行。
- `idempotency_key`：防止重复提交。
- `execution_token`：提交凭证。

### 处理业务状态变化

即使参数不变，外部状态也可能变化，例如：

- 商品价格变了。
- 库存变了。
- 毛利变了。
- 活动规则变了。
- 用户权限变了。
- 预算被其他任务消耗了。
- 商品被下架了。

因此 commit 时必须做二次状态校验。

处理方式可以分三类：

1. 非关键变化：允许执行。
2. 关键变化但仍在容忍范围内：重新计算并记录。
3. 关键变化且超出边界：中止执行，重新 prepare。

例如：

```text
prepare 时预计毛利率：18%
commit 时预计毛利率：3%
结果：中止执行，要求重新生成计划
```

这套机制可以叫 compare-and-commit，或者 state precondition check。

### 锁与有效期

有些场景可以在 prepare 后短暂锁定资源：

- 秒级发布动作。
- 批量改价。
- 活动报名名额。
- 广告预算扣减。

但很多电商运营操作的确认时间较长，不适合长时间加锁。

更推荐：

- 短 TTL 的执行计划。
- 版本号校验。
- 提交前重新校验关键指标。
- 状态变化则重新 prepare。

示例：

```text
计划有效期：10 分钟
超过 10 分钟未执行：自动失效
相关商品价格变化：自动失效
预算变化超过 5%：自动失效
毛利率低于阈值：自动失效
```

## 策略系统是什么

策略系统可以理解为代码层面的确定性规则系统，但不一定只是脚本。

更准确地说，策略系统是：

> 一套在模型之外运行的、可测试、可审计、可版本化的业务规则与风险控制系统。

它的核心目标是：

> 不相信模型的判断，只把模型当作建议生成器；真正能不能执行，由确定性系统裁决。

### 策略不是 prompt

Prompt 可以告诉模型：

> 不要创建超过 1000 元成本的优惠券。

但这不可靠。模型可能漏掉、误解、被用户绕过，或者在复杂上下文里算错。

策略系统应该在工具层强制判断：

```text
if estimated_cost > 1000:
    reject("单次优惠成本超过授权上限")
```

Prompt 是软约束，策略是硬约束。

### 策略的常见形态

代码规则：

```ts
if (coupon.maxCost > auth.singleCostLimit) {
  return deny("超过单次成本上限");
}

if (product.grossMarginAfterDiscount < 0.12) {
  return requireApproval("活动后毛利率低于 12%");
}

if (affectedProducts.length > 20) {
  return requireApproval("影响商品数超过 20 个");
}
```

配置化规则：

```json
{
  "rule": "coupon_cost_limit",
  "condition": "estimated_cost > authorization.single_cost_limit",
  "action": "require_approval"
}
```

规则引擎：

- 适合规则多、组合复杂、多业务线共用、需要版本管理和灰度发布的场景。
- 可以使用 Drools、Open Policy Agent、JsonLogic、自研 DSL 等。

工作流或审批流：

```text
单次预算 <= 1000：自动通过
1000 < 单次预算 <= 5000：商家确认
5000 < 单次预算 <= 20000：运营主管审批
> 20000：禁止
```

机器学习风控模型：

- 可用于异常操作检测、商家风险分、亏损风险预测。
- 即使使用模型，也建议外层再套确定性阈值。

### 策略系统回答的问题

策略系统通常回答三个问题。

能不能做：

- 用户有没有权限？
- 店铺状态是否允许？
- 商品状态是否允许？
- 平台规则是否允许？

能不能自动做：

- 是否在授权范围内？
- 成本是否超限？
- 影响范围是否过大？
- 是否不可逆？
- 是否属于高风险操作？

如果不能自动做，下一步是什么：

- 拒绝。
- 要求用户确认。
- 要求上级审批。
- 重新 prepare。
- 降级为草稿。
- 只给建议不执行。

### 策略输出

策略系统不应只返回 true/false，而应返回结构化决策。

```json
{
  "decision": "require_approval",
  "risk_level": "medium",
  "reasons": [
    "预计成本 1800 元，超过授权上限 1000 元",
    "影响商品数 35 个，超过自动执行阈值 20 个"
  ],
  "required_actions": [
    "user_confirm",
    "manager_approval"
  ]
}
```

常见决策包括：

- `allow`
- `deny`
- `require_user_confirmation`
- `require_manager_approval`
- `require_reprepare`
- `downgrade_to_draft`

### 早期落地建议

从 0 到 1 不建议一开始上复杂规则引擎，可以先做“代码规则 + 配置阈值”的策略服务。

推荐结构：

```text
Agent
  ↓
Tool API
  ↓
Policy Engine
  ↓
Business Service
```

或者：

```text
prepare_coupon_plan()
  ↓
normalize params
  ↓
estimate cost / margin / affected users
  ↓
policy_check(plan, auth_scope, business_state)
  ↓
return allow / approval / deny
```

早期每个写工具都内置一组策略检查：

- 权限策略。
- 授权边界策略。
- 成本策略。
- 毛利策略。
- 库存策略。
- 影响范围策略。
- 可回滚性策略。
- 频率策略。

策略系统最好在两个阶段执行：

1. prepare 阶段：判断计划是否可以生成、是否需要确认。
2. commit 阶段：重新判断权限、预算、版本和业务状态是否仍然满足。

## 最小可行版本

从 0 到 1 建议优先做：

1. 商品诊断后生成优化草稿。
2. 优惠券创建草稿。
3. 活动报名材料草稿。
4. 经营任务创建。
5. 低风险配置保存。

暂时不建议第一版做：

- 自动改价。
- 自动发布大额券。
- 自动投放预算。
- 自动批量下架。
- 自动修改大量商品。
- 无确认的运营托管。

第一版的目标应该是让用户感受到：

> Agent 帮我少走很多页面，少填很多表，同时最终决定权仍然在我手里。

## 结论

电商 Agent 写功能的合理设计，是从“辅助生成草稿”开始，在可信的工具、权限、风控和审计体系之上，逐步开放更高等级的执行能力。

写能力不是简单地让模型调用接口，而是建设一套“受控执行系统”。只有这样，Agent 才能既提升运营效率，又不放大商家的经营风险。

托管模式最合理的形态可以概括为：

> Standing authorization + policy gate + immutable execution plan + exception-based human-in-the-loop。

也就是：用户提前授权，Agent 自动行动；策略系统守门，执行计划锁定参数；只有越界、异常、高风险或不可逆时，才把人拉回环路里。
