# AI Agent 产品多出来的是智能边界与信任设计

## 核心观点

AI Agent 产品相比普通产品，多出来的不是“加一个 AI 功能”，而是要设计一个能在边界内可靠行动、失败可控、逐步获得用户信任的智能执行者。

普通产品主要考虑用户如何使用功能；Agent 产品还要考虑系统如何替用户判断、行动、犯错和被信任。

## 普通产品关注什么

普通产品的 Inception 通常重点关注：

- 为什么做
- 为谁做
- 解决什么问题
- 成功标准是什么
- 第一版做什么
- 明确不做什么
- 风险和依赖是什么

这些问题对 AI Agent 产品依然适用。但 Agent 产品的不确定性更高，因为它不只是提供功能，而是会参与任务判断、上下文理解、工具调用和执行动作。

## Agent 产品额外要考虑什么

## 1. 任务边界

Agent 不能只是“能聊天”或“很智能”，必须明确它替用户完成什么任务闭环。

需要想清楚：

- 它负责哪一段流程
- 输入是什么
- 输出是什么
- 什么情况算完成
- 哪些任务不属于它
- 什么情况下必须停下来问用户

关键问题：

```md
这个 Agent 到底替用户完成哪一个具体工作闭环？
```

## 2. 自治程度

普通产品通常由用户主动操作；Agent 产品会部分或全部代替用户执行。

自治等级可以分为：

- L1：只分析和建议，不执行
- L2：生成草稿，用户确认后使用
- L3：执行低风险操作，可撤销
- L4：自动完成任务，事后汇报
- L5：跨系统自主决策和执行

早期 Agent 产品不应急着全自动，通常更适合从建议、草稿、确认执行开始。

## 3. 工具权限

Agent 的能力不只来自模型，还来自它能调用什么工具、访问什么数据、执行什么操作。

需要定义：

- 能读哪些数据
- 能写哪些数据
- 能调用哪些 API
- 能不能访问互联网
- 能不能发邮件、发消息、改数据库、付款
- 哪些操作需要用户确认
- 哪些操作绝对禁止

这本质上是 Agent 的权限系统。

## 4. 上下文来源

普通产品更多依赖用户输入；Agent 产品高度依赖上下文质量。

需要考虑：

- 它需要哪些数据才能完成任务
- 数据来自哪里
- 数据是否完整、准确、及时
- 哪些上下文只在本次任务内使用
- 哪些上下文需要长期保存
- 哪些信息不应该被记住

Agent 的输出质量，很大程度取决于上下文工程。

## 5. 记忆机制

Agent 产品可能需要保存用户偏好、习惯、历史判断和任务经验。

需要区分：

- 短期记忆：本次任务内需要的信息
- 长期记忆：跨任务持续有用的信息
- 禁止记忆：隐私、敏感、过期或容易造成误导的信息

关键问题：

```md
Agent 应该记住什么，忘掉什么，什么时候更新记忆？
```

## 6. 人类确认点

Agent 产品不是越自动越好，而是该自动的自动，该确认的确认。

需要定义：

- 哪些步骤必须确认
- 哪些低风险步骤可以自动执行
- 用户如何审核 Agent 的计划
- 用户如何修改 Agent 的输出
- 用户如何拒绝或中断 Agent

确认点决定了 Agent 的可控感。

## 7. 失败处理

普通产品失败通常表现为报错；Agent 产品失败可能是误解、幻觉、错误推理、错误执行。

需要提前设计：

- 理解错任务怎么办
- 生成虚假内容怎么办
- 工具调用失败怎么办
- 执行到一半失败怎么办
- 结果质量不稳定怎么办
- 如何回滚、撤销、重试
- 如何向用户解释它做了什么

Agent 产品必须默认它会失败，并提前设计兜底机制。

## 8. 可解释性和审计

Agent 会代替用户做判断和行动，所以用户需要知道它为什么这么做。

需要记录：

- 输入是什么
- 使用了哪些数据
- 调用了哪些工具
- 做了哪些修改
- 哪些地方不确定
- 哪些操作经过用户确认
- 失败原因是什么

可解释性和审计会直接影响用户信任。

## 9. 评估标准

普通产品主要看使用率、转化率、留存和收入；Agent 产品还要评估任务质量和智能可靠性。

额外指标包括：

- 任务完成率
- 一次通过率
- 人工介入率
- 幻觉率
- 工具调用成功率
- 错误执行次数
- 用户撤销次数
- 平均任务成本
- 平均任务耗时
- 用户信任度

Agent 产品不能只看用户有没有点击，还要看 Agent 有没有把事情做好。

## 10. 成本与延迟

普通软件的边际成本通常较低；Agent 每次运行都可能产生模型、检索、工具和计算成本。

需要想清楚：

- 单次任务最多花多少钱
- 单次任务最长等待多久
- 是否需要异步执行
- 是否需要缓存
- 是否需要分层模型
- 高价值任务和低价值任务是否采用不同成本策略

很多 Agent 产品不是不能做，而是做出来以后成本结构不成立。

## 11. 信任设计

Agent 产品的核心门槛不是用户会不会用，而是用户敢不敢把事情交给它。

建立信任的方式包括：

- 先建议，再执行
- 高风险操作确认
- 结果可追溯
- 修改可撤销
- 明确展示不确定性
- 不夸大能力边界
- 让用户逐步授权更高权限

信任不是靠一句“AI 很强”建立的，而是靠一次次稳定完成任务建立的。

## 12. 安全与权限边界

Agent 一旦能读写数据、调用工具，就会引入更复杂的安全风险。

需要额外考虑：

- 越权访问
- Prompt injection
- 敏感信息泄露
- 错误调用工具
- 被外部内容诱导
- 跨系统操作风险
- 企业合规与审计要求

Agent 的安全边界通常比普通产品更复杂。

## 对照表

| 维度 | 普通产品 | AI Agent 产品额外要考虑 |
|---|---|---|
| 核心对象 | 功能和流程 | 任务闭环和智能行为 |
| 用户行为 | 用户自己操作 | Agent 替用户判断和执行 |
| 范围 | 功能边界 | 任务边界、权限边界、智能边界 |
| 数据 | 表单、状态、业务数据 | 上下文、记忆、外部工具数据 |
| 风险 | 功能错误、体验差 | 幻觉、误判、越权、错误执行 |
| 指标 | 使用、转化、留存 | 任务完成率、一次通过率、人工介入率 |
| 信任 | 易用、稳定 | 可解释、可撤销、可确认、可追踪 |
| 成本 | 研发和服务器成本 | 每次任务的模型、token、工具成本 |
| 安全 | 账号、数据、权限 | Prompt injection、工具滥用、敏感信息泄露 |

## 进一步的问题

- 这个 Agent 的最小任务闭环是什么？
- 哪些事情应该让 Agent 自动做，哪些事情必须让用户确认？
- 用户为什么会信任这个 Agent？
- Agent 犯错时，用户如何发现、理解、撤销和修正？
- 单次任务成本是否支撑商业模式？
